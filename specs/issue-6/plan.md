# Plan: Deploy to Cloudflare button and Workers Builds

Source: Issue #6
Status: Revised (1)
Tier: security — the change is build and deploy configuration (`wrangler.jsonc`, the `deploy` script Workers Builds
runs) and moves the Telegram bot token from the *Encrypted credentials* security area (D1) to a Worker secret.

## Problem / root cause

Seluna has no way into a user's Cloudflare account yet: `wrangler.jsonc` declares only name, entry point and
compatibility date, there is no D1 binding, no cron trigger, no `migrations/` directory, no `.dev.vars.example`, no
`deploy` script, and `README.md` holds only the placeholder comment `<!-- Deploy to Cloudflare button: placeholder -->`
(line 7). `src/index.ts` exports only `fetch`, so a cron trigger would invoke a Worker without a `scheduled` handler.

Claims of the issue and the orchestrator's note, checked:

- "D1 binding `DB` without a fixed `database_id` (provisioned by the button)" — **confirmed** in the Cloudflare
  documentation (`src/content/docs/workers/platform/deploy-buttons.mdx`, cloudflare-docs commit `7b23ded`, read in a
  scratch clone): the button provisions D1 databases and "update[s] the Wrangler configuration ... (e.g. database
  IDs)". The same page asks for "default values for resource names", so the binding gets `database_name: "seluna"`.
  Wrangler 4.151.0 also auto-provisions on `wrangler deploy` (`--experimental-provision` defaults to `true`,
  `wrangler-dist/cli.js` line 366570).
- "Secrets prompted by the deploy form ... declared in `.dev.vars.example` with a description each" — **partly
  confirmed**: the form reads the secret names from `.dev.vars.example` (dotenv), but the documented place for a
  description the form shows is `cloudflare.bindings.<NAME>.description` in `package.json`. The plan puts the
  description in both (a comment in `.dev.vars.example`, the form text in `package.json`).
- "Deploy command: `wrangler d1 migrations apply DB --remote`, then `wrangler deploy`" — **confirmed** as the
  documented pattern: the button pre-populates the deploy command from the `deploy` script in `package.json`, and
  the docs recommend migrating by binding name. Wrangler confirms the migration prompt with "yes" in CI
  (`confirm2`, `cli.js` line 139685, `isNonInteractiveOrCI` → `fallbackValue = true`).
- "There is currently no `migrations/` directory" — **confirmed**, and it matters: `wrangler d1 migrations apply`
  throws `No migrations present at <dir>` when the directory is missing (`getMigrationsPath`, `cli.js` line 238995)
  and logs `No migrations to apply!` when it exists without `*.sql` files (line 239297; files filtered by
  `migrations/*.sql`, line 65763). Git keeps no empty directory, so the directory needs a file that is not `*.sql`.
- "No scheduled handler" — **confirmed** (`src/index.ts` line 10–14).
- "`worker-configuration.d.ts` regeneration" — **confirmed** needed: `wrangler types` with the new binding adds
  `DB: D1Database;` to `__BaseEnv_Env` and changes the hash line, nothing else (checked in a scratch copy, where
  `npm run build` also listed `env.DB` and `vitest run` passed 91/91).
- "Dependency #4 already in `src/`" — **confirmed** (`src/router.ts`).
- Node.js on Workers Builds: the build image defaults to Node.js 24.21.0 (`workers/ci-cd/builds/build-image.mdx`),
  matching `engines.node` `24`; no `.node-version` is needed.

Related defect found on the way: [decision 0007](../../docs/decisions/0007-github-app-credentials-encrypted-in-d1.md),
`docs/ARCHITECTURE.md` (components, D1 tables) and `.squad/project.md` (*Encrypted credentials*) say the Telegram bot
token is stored encrypted in D1, while issues #6, #7 (the `secrets` table holds App ID, private key and webhook
secret only) and #9 (`TELEGRAM_BOT_TOKEN`) treat it as a Worker secret. The issues are the product owner's later and
consistent statement; the plan follows them and corrects the documents (0007 is unreleased — no `v*` tag exists — and
is edited in place). The guarantee "GitHub App credentials are only ever stored encrypted" is untouched.

### Runtime details no one can verify before AC6

Each is named so a failure at AC6 is recognized, and each fails closed:

1. **The button provisions the database and writes its id into the copy before the first build.** Documented, not
   observed. If it does not, `db:migrations:apply` fails with Wrangler's "Couldn't find a D1 DB named 'seluna'" and,
   because of `&&`, nothing is deployed (fail closed). Remedy then: a follow-up issue that changes the deploy
   order or adds a create step — not a change to this plan's guarantee that migrations precede the deploy.
2. **The form shows the descriptions from `cloudflare.bindings` and accepts the empty example values as "to be
   filled".** Documented for descriptions; the empty value is chosen so no placeholder can ever be deployed as a real
   secret.
3. **Workers Builds takes `npm run build` (`wrangler deploy --dry-run --outdir dist`) as build command and
   `npm run deploy` as deploy command.** Documented pre-population; the dry run only bundles and is harmless.
4. **A cron trigger on a free account:** two triggers, within the free plan's per-account limit; an account that has
   used up its cron triggers gets a failing deploy (fail closed).

## Approach

1. `wrangler.jsonc`: add `d1_databases` and `triggers` as in AC1 (Dev).
2. `npm run types` regenerates `worker-configuration.d.ts` (Dev).
3. `src/index.ts`: add the `scheduled` member with the signature below; body returns `Promise.resolve()` (Dev).
4. `migrations/README.md` (Dev), stating: migrations for the D1 binding `DB`; files `NNNN_<name>.sql`, applied
   in name order, each once, by `npm run db:migrations:apply` before every deploy; a released migration is never
   edited — a schema change is a new migration; the first migration follows in issue #7.
5. `.dev.vars.example` (Dev), exactly:

   ```ini
   # Random string of at least 32 characters, for example from a password manager or `openssl rand -hex 32`.
   # It is the password of the /setup page and the source of the key that encrypts the stored credentials;
   # changing it later means running the setup again.
   SELUNA_SECRET=
   # Token of your Telegram bot: talk to @BotFather in Telegram, send /newbot and copy the token it returns.
   TELEGRAM_BOT_TOKEN=
   ```

6. `package.json` (Dev): the two scripts of AC4, and

   ```json
   "cloudflare": {
     "bindings": {
       "SELUNA_SECRET": {
         "description": "A random string of at least 32 characters, for example from a password manager or `openssl rand -hex 32`. It is the password of the `/setup` page and protects the stored credentials. Keep it: changing it later means running the setup again."
       },
       "TELEGRAM_BOT_TOKEN": {
         "description": "The token of your Telegram bot. In Telegram, send `/newbot` to [@BotFather](https://t.me/BotFather) and copy the token it returns."
       }
     }
   }
   ```

7. `README.md` and `docs/setup.md` (Dev) as in AC5. `docs/setup.md` (English; issue #20 extends it into the full
   guide) has: **Before you deploy** — the bot token from @BotFather, a `SELUNA_SECRET` as described above, a GitHub
   and a Cloudflare account; **Deploy** — select the button, connect GitHub, the button creates an independent copy
   of the repository in your GitHub account (not a fork), creates the D1 database, asks for the two secrets, builds
   and deploys; open `https://<worker>.<your-subdomain>.workers.dev/health`, which answers with the version;
   **Updates** — every push to `main` of your copy builds and deploys it, after applying the database migrations;
   **Next steps** — the `/setup` wizard follows in a later version; until then the instance answers webhooks with 503.
8. `.gitignore` (Dev): replace the line `.dev.vars` with the four lines `.dev.vars*`, `!.dev.vars.example`,
   `.env*`, `!.env.example` (AC3).
9. Documentation updates listed below.

## Options considered

The options are recorded in [decision 0013](../../docs/decisions/0013-deploy-to-cloudflare-and-workers-builds.md):
the bot token as Worker secret vs. encrypted in D1; binding without id vs. a fixed id; migrate-then-deploy vs.
deploy-then-migrate; an empty `migrations/` with a README vs. a baseline migration; no `secrets.required` (Wrangler
4.151 would refuse a first deploy of a Worker whose required secrets are unset, `cli.js` line 176340, and the
button's order is undocumented); the daily time `17 5 * * *`. Plus, for the setup-guide link: a link to a new
`docs/setup.md` (chosen) vs. a link to issue #20 (a planning artifact on `main`) vs. a dangling link to a file #20
creates later (a broken link until then). And for the scheduled handler: a pure no-op (chosen) vs. a log entry per
run (behavior issue #18 defines together with its jobs).

## Architecture check

- *Each user's data stays in that user's own Cloudflare account* (decision 0005): strengthened — the button deploys
  into the user's account, the copy is the user's.
- *GitHub App credentials are only ever stored encrypted* (decision 0007): untouched; only the Telegram bot token,
  which the guarantee does not name, moves from encrypted D1 to a Worker secret (stored encrypted by Cloudflare,
  write-only through dashboard and API). Recorded in 0013 and in 0007.
- *An invalid signature has no effect*: unchanged; without `GITHUB_WEBHOOK_SECRET` the instance answers 503.
- *A release is created only by a `v*` tag* (decision 0009): unchanged; Workers Builds deploys the user's copy on a
  push to its `main`, which publishes no release.
- No other guarantee is touched; no Product Manager decision is needed.

## Security considerations

- [x] No limits on parsed input: the change parses no input.
- [x] No exception reaches a user: `scheduled` cannot throw; a failed migration is reported by Wrangler in the
  Workers Build log, which only the account owner sees.
- Secrets: no value is committed; `.dev.vars.example` holds empty values; descriptions contain no secret.
- The `deploy` script runs only in the user's own Workers Build with the user's own credentials; it adds no
  dependency and no permission.

## Out of scope / follow-ups

- For issues #7 and #8 (from Security N2): `SELUNA_SECRET` is both the `/setup` password and the source of the
  encryption key. The key must be derived with HKDF under its own `info` (never the raw secret), the login compares
  in constant time against a value that is not the key, and a missing, empty or shorter-than-32-character secret
  fails closed (the wizard refuses to start, nothing is decrypted). The orchestrator adds this as a comment to #7
  and #8, or the Lead of those issues reads it here in the working record.

- The cron jobs and dispatch by expression: issue #18.
- The full setup guide, manual setup with Wrangler (it must say that a hand-run `npm run deploy` on a new account
  needs the database first), troubleshooting: issue #20.
- Bringing upstream updates into a user's copy: issue #19.
- Reading `SELUNA_SECRET` and `TELEGRAM_BOT_TOKEN` in code: issues #7, #8, #9.
